# 中转按机器挂：端口转发与公网发布搬进设置

端口转发（Port Forward）与公网发布（Public Share，ADR 0014）原来都挂在项目上、放在右侧栏的「转发」面板里，按焦点项目显示。用得久了两个问题很明显：

- **同一台机器上开着几个项目，转发却各记各的**。三个项目都在同一台远端主机上，几条本地转发就散在三个项目下；想看「本机现在哪些端口通着哪台机器」得挨个切项目。转发本来就是机器之间的事，跟项目里是哪个仓库没关系。
- **同一个本地端口想在两个目标之间切换，只能删了重建**。本机 5432 有时要接 A 机的库、有时要接 B 机的——旧实现把同监听端口当冲突直接 409。

统称 **中转（Relay）**，见 CONTEXT.md。

## 决定一：挂载点是机器——本机或一台已保存的 SSH Host

- 端口转发挂 SSH Host（`host_forwards.host_id`）。两头必须落在一条 SSH 链路上，本机没有转发可言。
- 公网发布挂本机（`host_shares.host_id IS NULL`）或 SSH Host。原来的 `origin: local | remote` 就是「挂哪台机器」，所以字段去掉了：挂本机就是本机端口，挂主机就是经这台主机的链路桥到本机再发出去。cloudflared 仍只在后端本机跑（ADR 0014 决定二不变）。
- 没保存成 SSH Host 的连接（存量项目手写的 ssh_*）挂不了中转。要转发就先把它存成主机——主机本来就是「预先保存的连接配置」，中转是它的附属物。

隧道走**主机自己的那条 `SshLink`**（`SessionManager.getHostLink`，原本只给「浏览远端目录」用），不再走项目链路。一台机器一条连接，项目删了、项目链路断了都不牵连中转；主机链路断了由 `scheduleHostReconnect` 指数退避重连（只要还有启用中的中转就坚持），连上的 `"up"` 事件把该主机的规则拉起来。项目链路的重连回到只为「待接回的持久会话」服务。

规则启动前先 `getClient()` 把链路连上再开本机监听 / 本机桥。原来本地转发的监听器与 SSH 无关，主机明明连不上，规则却显示「运行中」，要等第一条 TCP 连进来才露馅；项目链路时代这个问题被会话掩盖了（会话早把链路连上了），主机链路没有这层掩护。

## 决定二：同端口可以存多条，同时只有一条生效

「同端口」按**监听真正落在哪台机器上**算（`sessions/relaySpec.ts`，纯函数有单测）：

| 类型 | 冲突范围 |
|---|---|
| 本地转发 | 所有主机的本地转发（监听都在后端本机） |
| 远端转发 | 同一台主机的远端转发 |
| 公网发布 | 同一台机器上发同一个目标端口的发布 |

只比端口不比监听地址：界面上只能填端口，127.0.0.1 与 0.0.0.0 的同号端口系统层面本来就互斥。

启用一条（新建时带 enabled、或 PATCH enabled:true）时，后端**先同步落库**把同槽位的其它 enabled 规则改成 disabled、再写自己这一行，然后才去异步地停旧的、起新的。两个并发请求各自启用同端口的两条时，库里任何时刻都只有一条 enabled，后到的赢；停在起之前，新监听器不会撞上旧的还没释放的端口。前端因此每次写完都重拉整张列表（`GET /api/relays`），不能只替换这一行。

「停旧起新」放在后台，响应里是 starting、轮询接结果：起一条要先把主机链路连上，主机不通就得等满 SSH 握手超时（15s），await 的话勾选框一直转。停的时候也不等**还在连主机**的那次尝试——每条规则有个代数，`stop()` 让它 +1，在途尝试连上（或超时）后见代数变了就自己退出、不写错误、不开监听。「A 机连不上、把本机端口切到 B 机」正是同端口切换的主要场景，不这样的话 B 要陪着等 A 的超时。已经连上、正在开监听的那一小段照旧等它开完再拆，端口才交接得干净。

没有做成「切换目标」的单选组：多条同端口规则各自有名字、方向、目标，本来就是独立的规则，勾选框就够用，界面在行上标「同端口 ×N」提示它们互斥。

## 决定三：放进设置，右侧栏的「转发」面板删掉

中转不跟焦点项目走以后，挂在项目视角的右侧栏就不对了。设置 →「连接」组新增「中转」页，排在「远端主机」后面：按机器分块，「本机」只有公网发布，每台主机有端口转发 + 公网发布。页面开着时每 3 秒轮询。原来的 ⌘⇧F / Ctrl+Shift+F / Alt+F 改成直接打开这一页（命令 `openRelays`），命令面板里是「中转设置」。持久化的右侧面板若停在已删掉的 `forward` 上，按「认不出的面板名退回默认」处理。

原生客户端同步：右侧栏去掉转发面板，设置对话框加同样的一页。

## 决定四：迁移旧规则，旧表删掉

`Db.migrateRelaysToHosts()`：旧表 `ssh_forwards` / `public_shares` 存在就并进新表再 DROP——靠「旧表在不在」判断，不用 settings 标记，老版本二进制若又建出旧表、加了规则，下次启动照样并过来。id 原样沿用、`INSERT OR IGNORE`，重复跑无害。

- 转发的落点：项目上的 `host_id`（主机还在才算）；存量项目没绑主机时按连接三元组（host / port / username）找一台一模一样的已保存主机。都找不到就丢弃并打日志——换个用户登录，远端监听的权限与可达地址都可能不同，不能猜。
- 发布：`origin=local` 挂本机（与项目是本地还是 SSH 无关）；`origin=remote` 同转发的规则找主机。
- 几个项目的规则并到一台机器上可能撞出同端口的两条 enabled：留最早建的那条，其余置 disabled。

删主机不再只删连接配置：先停掉挂在它上面的隧道，再连同规则一起删（`Db.deleteRelaysOfHost`，外键没开，级联在应用层）。改主机时**只有连接配置变了**（host / port / username / 认证方式 / 钥匙 / 密文）才换链路并重新拉起启用中的中转——只改显示名也拆一遍会让隧道无端断一下。

## 验证状态

纯函数（槽位、让位、迁移去重、旧规则找主机）与迁移本身（旧表 → 新表、DROP、重复跑、删主机级联）有单测；在用户真实库的副本上跑过迁移（5 条转发并到同一台主机、本机的公网发布挂本机）。真机验过（测试实例 + 真实 SSH 主机）：本地转发经隧道读到远端 sshd 的 banner；同端口第二条启用后第一条自动停、端口交接无 EADDRINUSE；界面勾选切换同样生效；只改主机名时已建立的 TCP 连接不断；改认证方式后链路重建、退避重连后恢复；远端转发从远端 curl 打回后端；后端重启后启用中的中转自动恢复；删主机后本机与远端的监听都释放。没验：SSH 链路中途断开后的拆桥与重连（逻辑沿用原 onLinkDown / onLinkUp）、挂主机的公网发布真实拿 URL（不想在测试里把服务发到公网）、Windows 远端。
